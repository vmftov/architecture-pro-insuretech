# Проблемы

- `core-app`, `ins-product-aggregator` и `ins-comp-settlement` тесно связаны. Это может затруднить развитие приложения, в т.ч. дальнейшее разбиение на микросервисы.
- `core-app` синхронно зависит от `ins-product-aggregator`, который, в свою очередь, синхронно зависит от API всех страховых компаний. В случае долгого ответа API, это может привести к каскадным сбоям и отказам клиентам.
- `ins-product-aggregator` работает батчингом и в случае проблем со связью или в API хотя бы одной страховой компании:
    - Сервисы, запрашивающие данные, будут вынуждены ждать пока не будут завершены все запросы.
    - Если произойдет сбой, не будут собраны данные и других компаний.
- Если `core-app` или `ins-comp-settlement` потребуется масштабировать:
    - Зто приведёт к возникновению дублирующих запросов на получение данных из `ins-product-aggregator`.
    - Сервис `ins-product-aggregator` также потребуется кратно масштабировать, т.к. он может не справиться с нагрузкой.
- Сервис `ins-comp-settlement` зависит от состояния `core-app`. Если `core-app` будет не доступен в момент вызова, это может нарушить работу `ins-comp-settlement` и финансовые расчеты.
- Ситуация усугубится при подключении новых страховых компаний.

# Решение

**Перевести взаимодействие данных сервисов на асинхронную модель:**

- Сервисы `core-app` и `ins-comp-settlement` больше не будут инициаторами запросов. Они станут подписчиками нужных топиков `Kafka`.
- Сервис `ins-product-aggregator` будет по расписанию запрашивать новые значения через API и отправлять их в `Kafka`.
- Сервис `ins-product-aggregator` будет отправлять данные каждой страховой компании в `Kafka` независимо друг от друга.
- Сервис `ins-comp-settlement` перестанет обращаться напрямую к `core-app`. Вместо этого `core-app` будет публиковать события о создании заказа в `Kafka`. Данные события будут использоваться `ins-comp-settlement` для взаиморасчетов.

**В качестве брокера выбрана `Kafka`, потому что:**

- В приложении отсутствуют сложные взаимодействия и интеграции по стандартным протоколам и "умный" брокер не нужен.
- Есть необходимость обработки одних и тех же событий несколькими подписчиками.
- Долговременное хранение событий может быть полезно при поиске и исправлении проблем и сбоев в сервисах.

**Асинхронное взаимодействие сервисов позволит:**

- Сделать работу сервисов независимыми от текущего состояния друг друга. Это упростит развитие приложения.
- `ins-product-aggregator` сможет выполнять запросы к сервисам контрагентов по одному и формировать события по ним отдельно. Сервисы, зависящие от этих событий, будут отрабатывать их по мере необходимости. Если эти данные потребуются другим (новым) сервисам команде не придется менять код сервисов.
- Устраняется зависимость сервисов от возможных задержек и сбоев при получении данных из API страховых компаний, т.к. они больше не будут напрямую зависеть от них.
- Устраняется проблема дублирования запросов при масштабировании.

**Возможные проблемы:**

- Если API страховой компании станет недоступным на долгое время, сервисы `core-app` и `ins-comp-settlement` не узнают о том, что цены могли стать неактуальными. Для устранения данной ситуации необходимо ввести TTL. Если цены определённой страховой компании долго не подтверждались, информировать клиентов о том что цены могут быть неактуальны или временно приостанавливать показ продуктов с устаревшими ценами такой страховой компании.

**Применяемые паттерны:**

- Для устранения проблемы двойной записи в сервисе `core-app`, при сохранении данных о заказе в собственную БД и публикации их в `Kafka` для `ins-comp-settlement` необходимо использовать либо паттерн Transactional outbox, либо Transaction log tailing:
    - В первом случае, команде нужно будет разработать отдельный микросервис вычитки данных из БД `core-db` и публикации их в `Kafka`.
    - Во-втором, настроить Debezium на работу с `core-db`. Также потребуется настроить Patroni (который был выбран в задании 1) на синхронизацию слотов.
    - Конкретное решение должна принимать команда разработки исходя из своих знаний и навыков. В качестве примера, на диаграмме показан CDC.
    - В обеих ситуациях рекомендуется использовать отдельную таблицу, для поддержания стабильности внутреннего API.
- Для устранения проблем с долгим ожиданием ответа от API страховой компании может быть использован `Retry` и `Circuit Breaker`. Однако их использование не обязательно, т.к. запросы будут выполняться редко и регулярно по расписанию.
