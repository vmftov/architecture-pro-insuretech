# Front to back интеграции

- Подача заявки осуществляется через обычный REST API. Запрос сохраняется в `core-db` и распространяется далее асинхронно. Клиенту возвращается идентификатор заявки, чтобы UI код смог сопоставить заявку с результататами.
- Получение результатов клиентом осуществляется 2 путями:
    - Пока клиент не закрыл браузер и/или пока ещё не все результаты получены, они пересылаются с сервера асинхронно через WebSocket, по мере получения данных от страховых компаний. Вместо WebSocket можно было бы использовать и SSE, но в браузерах более строгие ограничения на их общее количество. Учитывая что приложение публичное и передача не контролируется корпоративным фаерволлом, использование WebSocket предпочтительнее.
    - Если клиент закрыл браузер или сессия прервалась настолько, что все результаты за это время уже были получены, то они возвращаются клиенту в рамках обычного REST запроса.
- С учётом большого числа потенциальных клиентов (2,5 тысячи человек) потребуется внедрение `Rate Limiter` для повышения отказоустойчивости системы в моменты поднятия новых подов или достижения лимитов ресурсов. `Rate Limiter` должен быть серверным. Клиенту будет отображаться сообщение, что сервер перегружен с просьбой подождать. Также, с клиентской стороны будет использоваться паттерн `Retry` с возрастающей задержкой для автоматического возобновления соединения с сервером.

# Back to back интеграции

- `core-app` и `osago-aggregator` взаимодействуют асинхронно через отдельные топики в `Kafka`. При этом используется 2 типа событий: появление заявки от пользователя и ответ от конкретной страховой компании (кол-во ответных событий равно числу компаний). Т.к. используется модель publisher-subscriber, события с результатами по ОСАГО будут получать все инстансы `core-app`. Чтобы событие обработал только тот инстанс который держит WebSocket соединение с нужным клиентом, в изначальное событие с заявкой помещается идентификатор клиента. Он возвращается с результатом в ответных событиях от `osago-aggregator`. В результате событие с результатом обрабатывает только тот инстанс `core-app` который в текущий момент работает с этим клиентом, а остальные пропускают это событие.
- `osago-aggregator` потребуется база данных для хранения состояния опроса страховых компаний и устранения дублирований:
    - Если при отправке события с заявкой Debezium упадет и перезапустится, заявка может оказаться в очереди дважды или более раз. `osago-aggregator` сохраняет в БД идентификатор и данные заявки, чтобы гарантировать её обработку only once и не перегружать API страховых компаний.
    - `core-app` не знает какое количество страховых компаний доступно и публикует заявку один раз. `osago-aggregator` дублирует заявку всем страховым компаниям и сохраняет в БД идентификаторы по которым он впоследствии сможет с помощью Polling-а проверять состояние. Несколько инстансов могут одновременно работать с одной заявкой. Если инстанс агрегатора упадёт, другой инстанс продолжит Polling с "того места" где закончил предыдущий.
    - При получении результата от страховой компании, он сохраняется в Outbox, а запрос к страховой компании помечается выполненным в рамках одной транзакции. Затем результат оптравляется в `Kafka` с помощью `Debezium`.
    - Старые результаты заявок со временем удаляются, т.к. они не нужны для работы `osago-aggregator`.

`osago-aggregator` легко поддаётся HPA.

# Интеграция с API страховых компаний

- В `osago-aggregator` необходимо добавить Timeout равный 60 секундам, чтобы не ждать бесконечно ответ от страховой компании.
- Также, потребуется паттерн Retry, чтобы возобносить плпытки если API временно станет недоступен или возникнет кратковременный обрыв соединения.
- Т.к. согласно заданию, серверы страховых компаний бывают нестабильными, можно добавить Circuit Breaker чтобы в моменты высокой нагрузки не обращаться к упавшему серверу страховой компании, пока он не восстановится.
- Если у API страховых компаний есть ограничения на число входных заявок от агрегатора, то можно использовать паттерн Rate Limiter чтобы ограничить число запросов к API.
